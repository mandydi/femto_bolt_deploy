## 每次更新

1. 读取本次用户提供的脚本及明确改动要求，列出与当前部署版本的差异。新脚本是业务功能的依据；区分必须纳入的新功能、实时输入适配，以及现有等价性能实现。
2. 对二维码识别、单号关联、材质分类、坐标与八点几何等业务代码，只做用户要求的修改。保留已验证的后台点云预处理、Numba 投影与体素聚合、模型预热、静态 mask 缓存等性能实现；若需要改动其语义，先用同帧对比证明输出等价。
3. 本地做语法检查与针对改动的功能测试。二维码代码有变化时，核对源码并用合成单号测试；有现场二维码时再做实时识别测试。几何代码有变化时，用同帧、固定随机条件比较材质、中心点和 8 点结果。
4. 部署前在两台各自备份当前运行脚本；部署相同文件，核对 SHA256，重启服务并检查 `running`、`RestartCount` 与日志。仅在依赖确实缺失时安装；bind mount 的源码更新无需默认重做 Docker 镜像。
5. 先记录冷启动结果，再记录预热后的连续现场调用。包裹必须处于有效区域；无包裹或拟合失败的请求不能算业务成功。报告全部请求，包括失败与超过阈值的请求，不挑选最快样本。
6. 验证生产 JSON：`success`、`best_label`、`center_world`（3 个有限值）、`box_8pts_world`（8×3 个有限值）、`waybill_dict`（按新脚本约定）。生产 JSON 不含诊断 timing；测试报告保留 RTT、服务端计算、后台预处理和输入帧龄。

## 时延验收

- 指标是客户端从请求到拿到结果的 **RTT < 1.0 秒**；冷启动耗时单独报告，不混入预热指标。
- 默认做至少连续 5 次有包裹、成功返回的预热请求，逐次报告 RTT。出现超过 1 秒或失败时，不能宣称“稳定亚秒”，须定位最早耗时阶段并修复后重测。
- 后台预处理不计入请求 RTT，但必须同时披露预处理耗时和输入帧龄；不能把较旧画面包装成实时结果，也不能用复用上一请求的识别结果来换取低 RTT。
- 如果现场没有有效包裹或二维码，分别说明哪些业务项尚未现场验收；合成测试不能替代现场测试。
